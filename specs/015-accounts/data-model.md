# Data Model: Accounts and Sign-in

All shapes below are proposed. Keep auth-library storage mapped explicitly to this application model; do not treat provider profile fields as authorization.

## Account and registration

`accounts`: UUID `id`; display `email`; unique `emailKey` (trim and lowercase, no provider-specific dot/plus rewriting); `emailVerifiedAt`; lifecycle (`pending`, `active`); display name; `createdAt`; `authEpoch`; `settingsJson`; `settingsRevision`; consent version/digest and acceptance time. Store an explicit accepted privacy/terms version, not a boolean alone. Account id is permanent; email is mutable.

Map `accounts` to Better Auth’s user model and `auth_methods` to its account model through the documented Drizzle schema mapping. Better Auth may insert a user row before confirmation; that row has pending lifecycle and is not an active app account. A `pending_registrations` companion has email key, password hash or validated provider identity, consent receipt, signup-browser settings snapshot, expiry and browser-binding nonce. It is not an owner-capable account. Signup presents a pending/unconfirmed account to the user; completed account creation occurs only after email proof. This resolves FR-021's no-work pending signup rule together with the first-account claim: the first completed local account creation receives legacy work. Competing pending registrations cannot reserve an email or the legacy claim indefinitely. A verified provider can replace an unconfirmed password registration atomically; invalidate its sessions/tokens and never transfer its password. A pending registration cannot list, save or export work.

## Library mapping and mutation ownership

Use the documented Drizzle schema mappings for Better Auth user/account/session/verification models; extend its user with lifecycle/consent/settings and its account with explicit provider identity fields. Library adapter transactions own routine authentication writes. App lifecycle operations use the same SQLite connection with app-owned transactions; do not nest auth API calls inside `BEGIN IMMEDIATE` or assume library hooks share an outer transaction.

Intercept public signup/verification/email-change/deletion routes in the app facade; do not expose the library's stock mutating variants. Confirmation uses app-issued random tokens with stored SHA-256 digests, then one transaction consumes proof, activates the mapped user, settles collisions, attaches a staged method and performs the legacy claim. Stock Better Auth email verification uses signed JWTs and does not reject repeat confirmation, so it cannot substitute for this endpoint. Use library password hashing/verification utilities for staged password registrations; never implement scrypt parameters independently. After commit, a separate library session operation may sign in; its failure leaves a confirmed account recoverable through ordinary signin, not a half-claimed store.

Provider callbacks validate through the library but stage unlinked identities before user creation/linking. Database hooks reject direct creation/activation without a valid server-side consent operation. Final app transaction maps that staged identity to an existing explicitly authorized account or creates/activates the new one; no callback performs email auto-linking. A transaction rollback cannot leave an identity linked without consent/claim completion. Integration tests must attempt each blocked raw library endpoint and prove it cannot bypass these routes. Do not use a post-create hook to claim work after an account was already committed.

## Sign-in methods

`auth_methods`: id, account FK, kind (`password`, `google`, `microsoft`, `apple`), provider issuer and subject, provider-reported email and verification provenance, optional password hash, created time; optional encrypted Apple revocation material and key id. Unique `(issuer, subject)` for external identities; one password method per account. Identity is the validated issuer/subject pair, never email or display name. Discard Google/Microsoft access/refresh tokens after identity validation; no offline-access scopes. Apple is the explicit exception: retain only the revocation credential needed for disconnection, encrypted with Node AES-256-GCM under `AUTH_TOKEN_ENCRYPTION_KEY` (key id, random nonce and authentication tag stored alongside ciphertext). Never export it. At deletion move it into a private account-independent revocation queue, retry for at most seven days or until successful/expired, then erase ciphertext and account reference. Library method/session rows are deleted immediately; pending provider revocation cannot grant app access. Rotation retains the previous key only until queued credentials are re-encrypted or expired.

Password hashes use the library's salted adaptive scrypt implementation. Validate 10–128 Unicode characters before hashing, reject entries in a bundled, licence-recorded common-password list, permit paste and password managers. Rate-limit hash work. Adding/removing methods and changing credentials requires recent authentication. Check the count of enabled usable methods inside the unlink transaction. Disabling a configured method may leave an account with no usable ordinary method. A built-in confirmed-inbox recovery flow remains available independently of AUTH_METHODS; it is not provider signup or an email-match linking path. An active account’s verified inbox proof can issue a normal session without adding a password. Keep ordinary password signin/reset disabled when password is absent from AUTH_METHODS; offer inbox recovery instead. Removing the last enabled ordinary method remains refused; operator-disabled methods do not prevent recovery.

## Sessions, callback transactions and email tokens

`auth_sessions`: random opaque bearer token (the actual Better Auth session representation, not a digest), account FK, issued time, last-activity time, fresh-authentication time, absolute expiry, persistent flag and captured auth epoch. Private database and backup permissions protect these bearer values; never export or log them. Server checks the database on every personal request; no session cookie cache can bypass revocation. Nonpersistent sessions have no persistent cookie expiry and expire after 12 hours idle; persistent sessions have a fixed 30-day lifetime. Reauthentication rotates the token and updates fresh-authentication time. Reset, email change, deletion and global signout revoke the required sessions atomically.

`auth_transactions`: short-lived, single-use nonce; intent (`signin`, `link`, `reauth`); initiating browser/session/account/epoch for link or reauth; provider; PKCE/state/nonce metadata; sanitized relative return path; consent receipt. Validate signature, issuer, audience, expiry, state, nonce and PKCE using the library. Expire transactions after ten minutes. Never turn an unauthenticated callback into a link intent.

`email_tokens`: random token digest, purpose, subject account or registration id, target email key, expiry, used time and initiating auth epoch where required. One-hour expiry for confirmation/reset/change/recovery. GET renders a landing form; POST consumes the token, avoiding consumption by mail scanners. Email change applies only to its bound account and target; recheck uniqueness and epoch at consumption. A password-reset proof changes/adds a password only when password is enabled. A separate `recovery` proof targets one existing active account and its current confirmed email plus auth epoch. Consume it atomically, revoke all sessions/older recovery proofs and create a one-use session-issuance receipt. After commit, the auth session layer redeems that receipt once for a fresh, nonpersistent normal session of that account, independently of AUTH_METHODS, with the usual 12-hour idle limit and 15-minute freshness. Bind the receipt to an HttpOnly browser nonce and the post-revocation account epoch. Atomically settle it to one session id; within five minutes, a same-browser retry after a lost response returns that same session, never another session or a second proof consumption. Recheck account state/email/epoch at redemption; an expired or invalidated receipt requires a new recovery email. Never expose the receipt as a reusable URL, accept a client-selected account or create/link an account by email. Recovery works from a signed-out browser with no initiating session; no password is silently enabled. Unlink/reauth safeguards still apply; inbox proof is the recovery sign-in, not an unverified email claim.

`auth_throttle`: keyed digest of canonical account identifier and separately trusted source address, failure window/count and blocked-until. Five consecutive account failures trigger a 60-second cooldown, doubled on further failed windows up to 15 minutes; 20 failures per source in five minutes triggers the same schedule. Give nonexistent accounts the same counters and response; successful authentication clears the account counter. Reset requests have an independent five-per-hour destination/source limit, not the password lock. Do not trust arbitrary forwarding headers for source identity. Retain counters only for the active window plus cooldown, at most 24 hours.

## Account-owned work and auxiliary rows

Add indexed `owner_id` referencing accounts to analyses, diagrams, translations and parsing attempts. Ordinary inserts always derive it from the server actor. The only null ownership allowed is the quarantined legacy-claim state; database constraints/triggers and service checks reject new null-owner writes. Every query includes owner, including preliminary revision checks and conflict readbacks. Foreign rows never produce validation or revision details.

Owner-scope translation names `(owner_id, edition, book, chapter, nameKey)`, chapter preferences `(owner_id, edition, book, chapter)`, recency, creation receipts and attempt idempotency. Same attempt id from another owner must not be accepted as a successful retry; collision returns invalid/not-found without revealing the row. All owner-bound study auxiliary rows cascade on deletion; minimal account-independent completion-notice/status and provider-revocation receipts follow their separately defined expiry rules. Owner joins prevent a preference referencing another owner's work. Corpus tables never receive owners.

Sibling 010/011 storage is planned, not implemented today. Handle each existing table explicitly; its later migration must create ownership constraints and indexes from the start. The account export header names all four kinds and its final counts include zero for unavailable kinds. Imported records for unavailable kinds return per-record unsupported-kind refusals rather than being silently dropped. Integrate 012 English-line fields into the shared settings schema when it lands.

## Legacy ownership claim

`legacy_claim`: singleton state (`pending`, `complete`, `failed`), backup identity, claimed account id, counts/digests per existing table and completion time. Pre-listen migration backs up SQLite including committed WAL state, creates the pending quarantine, and verifies integrity. A pending local install serves only public material and account setup; personal reads/writes remain blocked. Live refuses pending or failed ownership state.

Before claim, take a private SQLite-consistent backup outside any transaction; serialize claim attempts and bind the backup to the candidate database state. Inside `BEGIN IMMEDIATE`, recheck state and first completed account, activate its pending library user row (or create a verified-provider user) with consent/method/signup-browser settings, assign every unowned row, verify counts and byte digests of documents/metadata, and mark complete. Only owner columns change: preserve ids, titles, passages, raw document strings, revisions and timestamps, even for content now invalid. Exactly one concurrent account wins; later accounts get no legacy rows. Rollback leaves all rows unowned. A claim failure places the process in fail-closed startup/claim failure state, stops accepting requests, retains the backup and requires a clean restart after repair; it never resumes serving personal routes.

## Settings and client identity

Extract the pure per-field settings validator from client-only `src/lib/settings.ts` for shared server/import use. Keep anonymous `vible.display` storage separate. Account settings are server-authoritative with revision-checked updates; invalid/missing fields default independently, including later fields. First completed local signup receives a validated snapshot from the creating browser. Other accounts begin with defaults unless settings are explicitly imported.

Each loaded work session, draft, debounce, outbox entry and response handler carries originating account id plus an opaque session-generation marker. Server actor comes only from the authenticated session; submitted markers can reject a stale save but never select an owner. Switching identity cancels sends, clears personal views and settings, and retains drafts in an isolated recovery buffer offered only to their originating owner or for deliberate download. Never retry those edits into another account. BroadcastChannel plus a storage-event fallback signals same-browser logout; visibility/focus/session recheck handles missed messages and browser history restoration.

## Delivery and account lifecycle operations

`account_operations` and `mail_outbox` hold idempotency key, purpose, bound account/registration, prepared mutation, destination, transport status and expiry. Local writes private files in `DATA_DIR/mail/` and never constructs an outbound transport. Live uses Node fetch to the Resend HTTPS email API with `RESEND_API_KEY` and a verified `MAIL_FROM`. Persist a message UUID as Idempotency-Key and an immutable request body; the service deduplicates only for 24 hours. Stop automatic ambiguous retries after that window, use local delivery receipts, and expose a deliberate resend operation. Do not log plaintext passwords or bearer links. Capture files intentionally contain links and are private, not web-served.

Separate proof-link messages from completion notices. For confirmation/reset/recovery/new-address proof, stage the operation and require local durable capture or live service acceptance before finalizing the pending proof operation. Immediate sending failure preserves active account/credential/work state; links are inert until finalization. Acceptance is not a promise of inbox arrival: remote mail and SQLite cannot share a transaction. A crash after send/before finalization may leave an inert link; idempotent retry cannot duplicate a mutation. Unsent proof operations expire after one hour.

For password/email change and deletion, recheck actor, freshness, typed email, owner and preview fingerprint inside the final app transaction. Commit the state change and a completion-notice outbox row atomically. Only the committed outbox is eligible for delivery; no external send occurs inside the mutation transaction or before its commit. Rollback leaves no notice to send. A concurrent deletion-preview mismatch returns conflict and sends no completion notice. The deletion notice stores destination/purpose/delivery id independently of the deleted account FK and contains no work or reusable credentials; account/method/session/work rows are still removed atomically.

After commit, attempt delivery/capture idempotently; a rejection, bounce or outage does not roll back the completed change. Return separate mutation and notification statuses (`complete`, `notice-pending`, `notice-sent`, `notice-failed`); make pending/failure visible to the operator and the deleting browser through a short-lived opaque status receipt that exposes no deleted work or sign-in. Retry pending notices for seven days with capped backoff; after exhaustion mark failed and report it, never falsely report delivery or restore the account. Keep minimum delivery/status receipts for seven days after terminal delivery status, then erase them. Outbox deletion during account cascades must exclude this minimal post-deletion notice. Do not rely on service idempotency after its 24-hour window: persist local state, mark ambiguous outcomes for operator review, and never blindly resend them with a new key.

Account deletion cannot erase an already downloaded export or offline operator backup. Document backup retention and recovery policy in the privacy text; normal reads and restored deployments must never resurrect deleted accounts without explicit operator recovery handling.

## Account export and import

Version-1 export is one UTF-8 newline-delimited JSON file (`.ndjson`), streamed from a consistent database snapshot. First line is `{ type: "header", format: "vible-account-export", formatVersion: 1, exportedAt, settings, kinds: ["analysis", "diagram", "translation", "parse-attempt"] }`; zero or more `{ type: "record", kind, record }` lines follow; a final `{ type: "end", counts, sha256 }` line covers the exact preceding UTF-8 bytes including line endings. Counts include zero for unavailable kinds; those kinds simply have no record lines. Each record includes source id, edition, document version, passage/word anchors, original timestamps and content; practice attempts include answer, source snapshot, comparisons and checked time. Exclude account identifiers, passwords, methods, sessions, tokens, consent and delivery logs. JSON escaping keeps user newlines within one record line; parse one bounded line at a time with standard JSON parsing, not a hand-built general streaming JSON parser.

Export one owner-consistent SQLite read snapshot without an aggregate record-count/file-size cap. Preserve legacy raw payloads, including those needing attention, and annotate validation problems without dropping them. Browser File.stream() and server request streams process the same single file incrementally; uploads are sequential chunks of at most 8 MiB with operation id, offset and SHA-256, staged privately outside web-served paths. Resume matching chunks idempotently; a new import operation creates new copies. Never load the whole file or report into memory. Check free disk before each chunk; pause with a resumable storage error instead of declaring the export invalid. Disk capacity and the existing per-kind save limits remain practical constraints, not aggregate import-format limits.

Preview streams the staged file to completion, validates header/version and end counts/digest before any work writes, and writes an indexed private validation report. Page reports at 100 entries; download the full report as a stream. New-version or malformed framing/digest failures are envelope errors before writes. Known record kinds use their shared save-envelope limits plus metadata; enforce line/header limits derived from those same validators, so a currently valid exported record is never refused merely for framing overhead. Stream legacy records needing attention without buffering them as valid work, and report them through the same per-record save validation rather than silently truncating the file.

Commit processes at most 1,000 records per bounded transaction/savepoint batch, with an independently resumable receipt per record: fresh UUID and revision 1, preserve valid study content and event timestamps. A refused record does not prevent later valid records. There is no total file-byte or record-count rejection: acceptance includes more than 10,000 records and more than 50 MiB in one file. Names are allocated within the destination owner namespace. Never use source owner/ids to select destinations. Recheck corpus/edition/version through the same kind validator at commit; any changed validity is reported with indexed reasons. Practice import validates stored historical snapshots without replacing them with a present-day regrade; factor a shared historical-record validator if 010 only has a submission validator. Delete abandoned staged files/reports after seven days, retain active operations with reported progress, and cascade their data on account deletion.

Import settings only after an explicit preview choice; default is to keep destination settings. This avoids silent changes and keeps file contents available for round-trip validation. Repeating an import intentionally creates another set of records; transport retries with the same operation key return the prior receipt. Apply settings once at completion, revision-checked; a conflict reports retained current settings and does not undo successful records.
